# ADR-0024: Caddy as the TLS-terminating reverse proxy (compose only)

Status: Accepted (ENG-224)

## Context
- The node serves plain HTTP and has no authentication ([ADR-0013](0013-p2p-over-http.md), [ADR-0021](0021-professional-grade-study-reference.md), [SECURITY.md](../../SECURITY.md)). ADR-0021 lists TLS among the concerns a market tool should cover.
- Geth's guidance for exposing RPC is the same shape: put the endpoints behind a reverse proxy that terminates TLS and rate limits, and firewall the RPC port. We want a worked example of that for `bwg`, not a claim of fitness for public use.
- The limiter keys buckets on `r.RemoteAddr` only and ignores forwarded headers (`internal/server/ratelimit.go`, pinned by `ratelimit_test.go`). Behind a proxy every public client arrives from the proxy's address.

## Options
1. **Caddy (chosen).** An automatic local CA (`tls internal`), one-file configuration, Apache-2.0, runs as a separate service. Cost: one more image to pin and one more config format.
2. **nginx.** Certificates must be generated by hand (openssl or mkcert), which tempts committing keys to the repository. Cost: a certificate step in every run and a key-handling rule.
3. **TLS in the node with `crypto/tls`.** Out of scope for the roadmap: it puts key handling in the node, adds flags and reload logic to a hand-written core, and peers would still speak plain HTTP.

## Decision
- `compose.tls.yml` is a standalone stack (not a profile of `docker-compose.yml`: a profile cannot remove the `127.0.0.1:18081` port that base `node1` publishes). Run it as `docker compose -p bwg-tls -f compose.tls.yml up -d --build`. The base compose file and `e2e/` are unchanged.
- Services `node1`, `node2`, `dashboard` and `caddy`. Nodes and dashboard are on an `internal: true` network with no published port; only `caddy` is published, on `127.0.0.1:18443` (node API and explorer) and `127.0.0.1:18444` (dashboard).
- `proxy/Caddyfile` allows by method and path. Exposed on 18443, `GET`/`HEAD` only: `/health`, `/blocks`, `/headers`, `/mempool`, `/block/*`, `/tx/*`, `/balance/*`, `/address/*`, `/contracts/*`, `/events`, `/explorer`, `/explorer/*`. Everything else (`/p2p/*`, `POST /tx`, `POST /mine`, the legacy routes, `/metrics`, any other method) gets `403` with the plain-text body `blocked by proxy`. The dashboard site allows `GET`/`HEAD` on any path. Both sites add `Strict-Transport-Security`, `X-Content-Type-Options: nosniff`, `Referrer-Policy: no-referrer` and drop `Server`.
- The local CA and certificates live only in the `caddy-data` volume; no key or certificate is committed. `scripts/tls-smoke.sh` verifies the setup with `curl --cacert`, never `-k`.
- ADR-0021 criteria:
  1. Works around the core: it is a separate service in front of an unchanged node.
  2. Widely used, actively maintained, Apache-2.0, runs as a separate service (the image is pinned to `caddy:2.11.7`).
  3. Runs as a separate service in compose; no Go code imports it and no global state is added.
  4. **No module is added to `go.mod`** (direct or indirect), so `govulncheck` is unaffected.
  5. TLS termination teaches nothing about blockchains and hand-written TLS would be worse than the dependency.

## Consequences
- The node itself still has no TLS and no authentication; peers still speak plain HTTP on the internal network. The proxy hides write and p2p routes, it does not authenticate anyone.
- The limiter is per `RemoteAddr`, so behind the proxy `RATE_LIMIT` is one global cap shared by all public clients, while the dashboard and peers (which reach the node directly) keep their own buckets. Reading `X-Forwarded-For` safely needs a trusted-proxy rule and its own ADR (ENG-259).
- Rate limiting inside Caddy needs a third-party plugin build and is not done.
- README and SECURITY.md are updated in the same PR (ADR-0021 consequence). Not audited and not for public deployment.
