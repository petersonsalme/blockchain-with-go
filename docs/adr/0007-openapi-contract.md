# ADR-0007: Describe the HTTP API in an OpenAPI spec and generate the Go client

Status: Accepted (Lead-Opus, 2026-10-20, ENG-34)

## Context
- The HTTP API was documented only in the README; nothing checked that the README matched the server.
- ENG-33 added five routes, so the surface is now large enough to drift.
- AGENTS.md forbids heavy dependencies without need.

## Options
A. `openapi.yaml` + client generated by oapi-codegen + contract test with kin-openapi: two module requirements (`oapi-codegen/runtime`, `kin-openapi`). B. Spec + hand-written client: one requirement, but the client drifts silently. C. Spec validated only by a Node linter in CI: no Go dependency, adds Node to CI, does not test server adherence.

## Decision
Option A.
- `openapi.yaml` (OpenAPI 3.0.3) at the repository root is the HTTP contract. Handlers stay hand-written; no server code is generated.
- `internal/server/contract_test.go` validates every declared (operation, status) pair against `Server.Handler()`.
- `client/` is generated with a pinned `go run .../oapi-codegen@v2.8.0`; CI fails when regenerating it produces a diff.

## Consequences
- Any change to a route, status or JSON field must update `openapi.yaml` in the same PR, or the contract test fails.
- Generated code (`client/client.gen.go`) is excluded from the coverage floor and from mutation testing.
- OpenAPI 3.1 is not used, because oapi-codegen does not support it.
